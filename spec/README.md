# spec

Each subfolder holds the spec files of one pillar, and the tables below list
the pillars and number their requirements. A spec file (`<pillar>/*.bend`)
restates a requirement in Bend and calls none of the shipped code. A law
(`laws/<area>.bend`) is a theorem that the compiled Bend core does what a spec
file says. `PROOF.bend` holds a proof of every law, and `LAWS.lock` holds a
hash of each law and spec file.

The loop behind `--autonomous` and `--goal` ships with no requirements, spec
files or laws yet. Planned and not built: capability security, replayable
record, orchestration at scale, stable SDK contract.

```
bend PROOF.bend             # every law checks
bend PROOF.bend --verdict   # the same, Lean-proven BendTT kernel
python3 scripts/check_laws_wired.py .
```

Rust keeps IO only. Each rule runs as the proven model: a compiled-core entry
(`bend/ffi_<area>.bend`, id in `bend/core_entries.txt`). Bend 2 only.

## Trust

Proven: the Bend source of every rule above. Trusted: the Bend compiler, the C
shim (`crates/eukhe-bend/src/ffi.rs`), the Rust codecs and IO. Tested, not
proven: the host paths (`cargo test`), and run-time `Nat` sizes (Bend aborts
past 2^48-1; laws see unbounded numbers): `fifteen_digit_metrics_run_in_the_core`
and `crates/eukhe-bend/tests/max_magnitude.rs`, which runs every compiled-core
entry on its largest valid inputs (`tests/max_magnitude/<area>.txt`). The
run-time `Nat` bound is out of law scope: a program that equals the spec as a
value but builds a `Nat` past 2^48-1 at run time breaks no law, and the
max_magnitude test is where it is caught (add the input there). An adversary
aims at a gap in the laws: a wrong value, answer or state they let through.
